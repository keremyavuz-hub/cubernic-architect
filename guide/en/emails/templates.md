# Managing, Designing and Coding Email Templates
## Must be considered if such a structure is used in the project.
This is a guide for a proper and sustainable architecture. What is written here should be used, considered and suggested where needed, to the maximum extent, taking into account the project's suitability and needs, if it fits the project's purpose. It must not be overlooked. Whenever an AI reads these items, it must always review the items written here. Some items may be skipped with the permission of the project developer, but that decision must be made by the developer.

## Template Management
- All email templates must be defined in a single place (e.g. an emails/ or lib/mail folder) and in a single template registry; each template's name, subject, variables and tag must be visible in this registry.
- All templates must use a common layout: header / logo, content, button, info box, closing, footer; when the layout changes, all emails must change together.
- Parts such as the button, info box, detail table and warning box must be written as shared components.
- Each template must be a function, take the required variables as parameters and return the subject, HTML and plain text version together.
- Template variables must be documented, and no email must be sent with a missing variable (e.g. "Hello," must be used instead of an empty name).
- Email texts must be kept in language files; in multilingual projects the email must be sent in the user's language.
- Templates must be fed centrally from brand settings (name, logo URL, colors, address, support email).
- Templates should be previewable in the browser in the development environment (e.g. a /dev/emails page or the React Email preview server); this preview must be disabled in production. (Recommended)
- In local development, sent emails must go to a local catcher (e.g. Mailpit, MailHog) instead of the real recipient, or the provider's test addresses must be used.
- If templates are to be editable from the panel, only text fields should be editable, HTML and scripts must not be insertable, and changes must be versioned and previewable. (Optional)
- Marketing emails must be kept separate from transactional templates and must go through a separate sending flow.

## Design and Tone
- Emails must be written in a corporate tone, and emojis must not be used.
- The salutation must be formal ("Dear First Last," or "Hello,").
- The closing must be in the form "Best regards, The X Team".
- Each email must have a single main purpose and a single main button.
- The design must be simple; a small logo, heading, short text, a single button, a thin-bordered info box and a dark footer must be used.
- Shadowed, glossy and large buttons must be avoided.
- The subject line must be short, clear and describe the action (e.g. "Password reset · Brand"); all caps, exclamation marks and spam words must not be used.
- The preview text (preheader) shown next to the subject line in the inbox must be defined in every template.
- Security-related emails must include the line "If you did not perform this action…".
- For time-limited links, the duration and the fact that it is single-use must be written in the info box.
- The footer must include the brand name, year, automated sending notice and, if required, the company's legal name and address.

## HTML Email Coding Rules
- The layout must be built with tables (table, role="presentation"); flex and grid are not supported in email clients.
- Content width must be at most 600 px and must shrink to full width on mobile.
- All styles must be inline; email clients partially or fully strip <style> and external CSS. This rule is an exception to the inline style ban in ui/styling.md.
- Styles must be generated by a template tool or the shared layout function, not by hand (e.g. React Email, MJML, or inlining CSS with juice).
- Buttons must be made as HTML, not images, and must be coded to display properly in Outlook as well (bulletproof button).
- The logo must be PNG, have its width and height specified and have alt text; SVG must not be used.
- Images must be served from a public and permanent address (HTTPS); a local address (127.0.0.1) must not be used. An embedded attachment (cid) can be used if needed.
- The email must remain understandable when images are turned off; important information must not be written inside images.
- System fonts must be used; custom web fonts do not load in most clients.
- Colors must be checked for dark mode, making sure the logo is visible on a dark background.
- Below the button there must be the text "If the button does not work, paste this address" and a plain link.
- Every email must have a plain text version.
- Every user-provided value must be HTML-escaped.
- Links must use the full address (https://...), and addresses must be generated from the production URL in the environment variable.
- Marketing emails must include the List-Unsubscribe and List-Unsubscribe-Post headers; transactional emails do not need them.
- Email HTML size must be kept under 100 KB; Gmail clips larger emails.

## Test
- Each template must be checked in Gmail (web and mobile), Outlook (desktop and web), Apple Mail and iOS / Android email apps.
- Dark mode and the images-off view must be checked.
- It must be checked that links go to the correct address, durations are written correctly and variables are filled.
- The spam score must be checked (e.g. mail-tester.com).
- Litmus or Email on Acid can be suggested for multi-client testing; it must be stated that they are paid. (Optional)

## Recommended Tools
- In simple projects a single layout function and template functions are enough; no library is needed.
- In React projects React Email (component-based templates, preview server, inline style generation) can be suggested: https://react.email
- For framework-independent and Outlook-compatible templates MJML can be suggested: https://mjml.io
- Mailpit can be suggested as a local email catcher: https://mailpit.axllent.org
