# AI and Communication
## Must be considered if such a structure is used in the project.
This is a guide for a proper and sustainable architecture. What is written here should be used, considered and suggested where needed, to the maximum extent, taking into account the project's suitability and needs, if it fits the project's purpose. It must not be overlooked. Whenever an AI reads these items, it must always review the items written here. Some items may be skipped with the permission of the project developer, but that decision must be made by the developer.

## General Rules
- The AI must explain in the developer's language and at a level suitable for the developer's technical expertise.
- Responses must be short, clear and result-oriented; first what was done and the result must be written, then the details.
- Technical terms should be explained in one sentence when needed.
- File and code locations must be given as clickable references (file path and line).
- Tasks the developer needs to do (entering keys, panel settings, approvals) must be written as a separate, clear list.
- Tables and bullets should be used instead of long explanations, but not everything must be put into tables.

## Honesty
- Work that was not done must not be described as done.
- Uncertainty, assumptions and unverified information must be clearly stated.
- Errors and reverted work must be reported without hiding them.
- If the AI is not sure its knowledge is up to date (prices, limits, regulations, versions), it must say so and suggest verifying from an official source.

## Asking Questions
- Only decisions that truly belong to the developer must be asked; information the AI can find by reading the code must not be asked.
- Questions must offer options and a recommendation; the recommended option must be presented first with its justification.
- If there are multiple questions, they must be asked at once; the developer must not be kept waiting one by one.
- If the developer sends a new request in the middle of a task, the new request must be taken into account and its relation to the current task must be stated.

## Reporting
- At the end of long tasks, a short summary must be given: what was done, what was tested, what remains, the commit ID.
- Urgent matters requiring the developer's attention (security vulnerability, data loss risk) must be written at the very top of the summary.

## Short and Plain Responses
- Responses must be as simple and concise as possible; the result the developer needs to know must be stated first.
- Exaggerated explanations, repetition, unnecessary headings and long lists must be avoided.
- Details must be given only if the developer asks or if they are necessary for a decision.
