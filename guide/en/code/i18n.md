# Language Files and Internationalization
## Must be considered if such a structure is used in the project.
This is a guide for a proper and sustainable architecture. What is written here should be used, considered and suggested where needed, to the maximum extent, taking into account the project's suitability and needs, if it fits the project's purpose. It must not be overlooked. Whenever an AI reads these items, it must always review the items written here. Some items may be skipped with the permission of the project developer, but that decision must be made by the developer.

## General Rules
- All texts visible in the UI (headings, buttons, labels, error messages, email texts, notifications) must not be hardcoded; they must be kept in language files.
- Even if the application starts in a single language, texts must be moved into a language file from the start; extracting them later is much more expensive.
- Language files must be separate per language (e.g., locales/tr.json, locales/en.json) and must follow the same key structure.
- Keys must be meaningful and hierarchical (e.g., auth.login.title, errors.rate_limited); the text itself must not be used as the key.
- When inserting variables into text, placeholders must be used instead of concatenation (e.g., "Try again in {minutes} minutes").
- A standard format such as ICU MessageFormat must be used for language rules like singular / plural and gender.
- Validation rules and server errors must also return keys / codes rather than text; the text must be selected from the language file in the UI.
- A missing translation key must produce a warning in development and fall back to the default language in production.

## Formatting
- Date, time, number and currency must be formatted with the built-in Intl API, not manually in code (Intl.DateTimeFormat, Intl.NumberFormat).
- Upper / lower case conversions must be done per locale (in Turkish, toLocaleLowerCase('tr-TR'); the İ / ı issue).
- Sorting must be done per locale (Intl.Collator).
- The time zone must be selected per user or business, and UTC must be stored in the database.

## Other Languages and Directions
- If right-to-left languages (Arabic, Hebrew) are supported, layout should be done with logical CSS properties (margin-inline-start, etc.). (Optional)
- On multilingual sites, URL structure (e.g., /en/...), hreflang tags and a language switcher should be designed. (Optional)
- Terms, privacy notices and emails must also be managed with language file / versioning logic, and each language's legal text must be checked separately.

## Recommended Platforms
- For simple projects, a language file and a small translation function are enough; no library is needed.
- In Next.js projects, next-intl may be suggested if needs grow; react-i18next for React projects, i18next for general JavaScript.
- If working with translation teams, translation management platforms such as Crowdin, Lokalise, Tolgee (open source) may be suggested; the cost must be stated to the developer.
